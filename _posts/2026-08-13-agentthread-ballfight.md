며칠 전에 James한테 DM이 왔다. NousResearch/hermes-agent를 fork해둔 걸 보고 James가 직접 연락한 거다. 자기가 만든 AgentThread를 체험해보라고, $100 크레딧을 준다고 했다.

![초대 메일](/assets/agentthread-invite-email.png)

## AgentThread가 뭐 하는 도구인가

AgentThread는 호스팅된 Hermes다. 멀티플레이어가 붙은 버전이다.

Hermes는 로컬에서 돌아가는 오픈소스 AI 에이전트다. AgentThread는 이걸 웹 서비스로 감싼 거다. 채널을 하나 만들면 그 채널마다 독립된 컨테이너가 뜨고, 거기서 Hermes가 돌아간다. 채널 안에서 AI한테 코딩을 시키거나 배포를 맡기면, 결과물은 `keepconcentration.agentthread.ai` 같은 public URL로 바로 호스팅된다.

친구나 동료를 초대해서 한 채널을 함께 볼 수도 있고, AI가 작업하는 과정을 모두가 실시간으로 지켜볼 수 있다. 협업이 가능하다는 점이 일반 Hermes랑 가장 큰 차이다.

단순 비교하면 이렇다:

|  | Hermes | AgentThread |
|------|--------|-------------|
| 설치 | 필요함 (로컬 셋업) | 없음 (브라우저) |
| 공유 | 혼자 씀 | 채널에 사람 초대 가능 |
| 호스팅 | 직접 설정 | `*.agentthread.ai` 자동 |
| 프로세스 관리 | 내가 통제 | 서비스가 통제 (불안정) |
| 오케스트레이션 | 칸반, worker 프로필 분리 | 없음 |
| 문서 | 있음 | 거의 없음 |
| 오픈소스 | MIT 라이선스 | 아님 |

Hermes는 모든 걸 직접 통제한다. 대신 셋업과 호스팅도 내가 한다. AgentThread는 버튼 몇 번이면 준비된다. 대신 아래에서 도는 프로세스나 배포 상태는 보이지 않는다. 이 차이가 뒤의 삽질로 이어진다.

AgentThread는 AI 에이전트한테 코딩을 맡기는 서비스다. 그냥 써보기만 하면 아까우니까 실제로 뭔가 만들어보기로 했다.

## 도전: 볼 파이트 게임 만들기

에이전트한테 "볼 파이트"라는 게임을 만들어달라고 했다. 물리 엔진 기반으로 공들이 자동으로 싸우는 게임을 상상했는데, 에이전트가 18페이지짜리 기획안을 뽑아왔다. 무기 3종, 업그레이드 시스템, 경기장까지 다 구상해놓고는 바로 MVP 구현까지 해줬다.

![Ballfight ORBIT 모드](/assets/agentthread-ballfight-orbit.png)

여기까지는 나쁘지 않았다. 근데 실제로 만져보니 삽질할 지점이 한둘이 아니었다.

## 삽질: 이런저런 문제들

### 줄번호가 화면에 그대로 노출

리팩터링 중에 파일 읽기 줄번호가 그대로 HTML에 박혀서 사용자 화면에 나타났다. "화면에 1, 2, 3, 4 같은 숫자들은 뭐야" 하고 물어봐야 했다. 파일을 읽은 결과를 그대로 렌더링에 흘려보낸 흔적이었다.

### 프로세스 라이프사이클이 꼬임

포트 3000에 구버전이 계속 떠있는데, 에이전트가 자기 게이트웨이를 재시작하지 못했다. "수정 완료"라고는 하는데 실제 접속하는 public URL은 옛날 코드였다. `npm restart`로 겨우 해결했다. 로컬에서 코드를 고친다고 배포된 서버가 자동으로 갱신되지는 않는데, 그 갭을 에이전트가 스스로 못 메웠다.

### 모델 전환이 안 먹힘

`/model Sol`로 바꿔달라고 했는데 실제로는 Luna가 계속 돌고 있었다. "지금 모델 뭐야" 물어보면 Luna라고 답은 하는데, 정작 전환 요청은 반영이 안 된 상태였다. 다시 확인 요청하고 "Luna 맞습니다" 정정받는 과정을 거쳐야 했다.

![모델 전환 실패](/assets/agentthread-model-switch.webp)

### 공들이 갑자기 다 사라지는 렌더링 버그

BOUNCE CHAOS 모드에서 공들이 한 프레임 동안 뿅 하고 다 사라졌다가 다시 나타나는 버그가 있었다. 에이전트는 이 버그를 "18/18 테스트 통과"라고 보고했다.

이게 계속 걸리는 부분이다. 그 테스트는 기술적으로 틀리지 않았기 때문이다. 18개 테스트 전부가 물리 수학과 렌더링 한 프레임만 검증했고, 프레임 사이의 순간 상태는 보지 않았다. 테스트는 코드를 검증했지만, 실제 화면에 보이는 건 검증하지 못한 셈이다.

![BOUNCE CHAOS 렌더링 버그](/assets/agentthread-ballfight-bounce-chaos.png)

### "완료됐다"는 말을 못 믿게 됨

TOOL ACTIVITY 창이 "Reading index.html..." 같은 진행 표시만 띄우고 실제 응답 없이 끝나는 경우가 반복됐다. 15/15 테스트를 통과했다고 보고했는데 실제 public URL은 깨져 있던 적도 있었다. 에이전트 쪽 "Done" 신호랑 실제 배포 상태가 따로 놀았다.

## 피드백: 창업자한테 정직하게

James가 "10분 통화로 피드백 달라"고 했는데, 영어 통화는 부담스러워서 이메일로 정리해서 보냈다. 겪은 문제 그대로 다 적었다.

![피드백 메일](/assets/agentthread-feedback-email.webp)

- Process lifecycle management
- Local/hosted sync gap
- Tool activity가 실제 응답을 대체하는 문제
- "Done" 신뢰성
- Model switching
- 문서 부족

좋은 말만 늘어놓기보다 실제로 걸린 지점을 그대로 전달하는 쪽이 맞다고 생각했다. 그래도 방향성은 진짜 좋다고 마무리했다. 코드 짜는 것까지는 이제 AI가 잘한다. 문제는 그 코드가 실제로 돌아가는지, 정말 끝난 건지를 확인하는 데서 계속 사람 손이 필요하다는 거였다.

## 소감

AI랑 게임 만드는 게 하루 만에 되는 시대다. 근데 아직 프로세스, 배포, 신뢰성은 사람 손이 많이 간다. AgentThread는 방향이 좋아서 나중에 다시 써볼 거다.
